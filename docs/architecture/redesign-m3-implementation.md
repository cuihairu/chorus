## M3-5 后续已落地：动态 GameServer 目录（FIX-SCHED-01，2026-10-30）

M3-5 时代的 `ClusterDirectory` 只吃 `CHORUS_GAME_ENDPOINTS` 静态配置（「seeded, not discovered」）：新增/重启实例要重启 ControlServer 才被发现，死实例的地址永远留在轮询集合里。FIX-SCHED-01 把 game-host 半边改成**由有效进程报告维护**：

- **存储侧 incarnation 语义修正**（`RedesignControlStore.ReportProcessAsync`）：原 ON CONFLICT 谓词要求 `started_at` 相等且序列递增——同实例 id 重启（新 started_at、序列归 1）的报告会被**永久拒绝**，死行还占着旧 endpoint，动态目录根本无从收敛。修正为「新 incarnation（更晚 started_at）接管本行，或同 incarnation 序列递增」，SET 清单补上 `started_at`（原先不在 SET 里，导致重启只换 endpoint 不换 incarnation 时钟，旧 incarnation 的重放反而被放行——探针实证后修复）；旧 incarnation 重放与序列回退仍拒。新增 `ListGameHostReportsAsync(freshnessSeconds)`：`control.process` JOIN `control.deployment`（role=game-server）、endpoint 非空、lifecycle=Running、observed_at 在新鲜窗内——「有效进程报告」的定义。

## 按就绪与容量选择目标已落地：准入词 + 排空棘轮 + 目录资格分离（FIX-SCHED-02，18935f5）

M3-5 的 `ClusterDirectory` 只维护「可达性」：谁在报告、端点在哪、证据是否新鲜。它**看不到**三样调度事实——host 的 readiness 自报在目录边界被丢弃、admin 排空是瞬时字（宿主下一次自报就把 lifecycle/admission 盖回去）、宿主容量只在 `PrepareRoom` 时被动拒绝（FIX-PERF-07 的预算）。后果是调度器把新房塞给 NotReady/已排空/已满的宿主，让宿主每轮都以 `ResourceExhausted` 回答。FIX-SCHED-02 把「准入」建成显式的、端到端的词：

- **准入词汇表**（`ProcessAdmission`，新）：`Accepting`（规范）、`Full`（宿主自报容量）、`Draining`（管理员单向棘轮）；遗留 `"Open"` 入站容忍（`AdmitsNewRooms` 对 Accepting/Open 为真），未知词 fail-closed——配置写错不会变成「无限接纳」。
- **GameServer 自报链**：`RoomAdmissionBudget.WouldRefuse(degradedRooms)` 是 `TryReserve` 的纯谓词（同两维：测得负载/活跃房数），**不占槽**——自报永不移动容量；`RoomRuntime.AdmissionState` 据此返回 `Full`/`Accepting`；`ProcessSelfReporter` 新增 admission 回调，GameServer 接线 `() => runtime.AdmissionState`（原硬编码 `"Open"`）。宿主在预算满时自报 `Full`，调度器在**提供房之前**就不再选它。
- **排空单向棘轮（SQL）**：`ReportProcessAsync` upsert 的 `admission=CASE WHEN control.process.admission='Draining' THEN 'Draining' ELSE excluded.admission END`——排空是管理员的词，宿主乐观自报（预算有头寸时总说 Accepting）顶不住；重新投产是管理动作（un-drain RPC open，见诚实边界）。`DrainProcessAsync` 同写 `lifecycle+admission='Draining'` RETURNING admission；重复排空回复改读 `ReadProcessAdmissionAsync`（原 `ReadProcessLifecycleAsync` 读的是宿主自报随时翻回的 lifecycle，重复排空会错报）。
- **feed 语义**：`lifecycle IN ('Running','Draining')`——排空宿主**留在**目录（其既有房还需控制面够到）；只有 Exited 是真离去。
- **目录 membership/eligibility 分离**：条目新增 `readiness`/`admission`；`EligibleHosts` = 证据新鲜 + `Ready` + `AdmitsNewRooms`；`NextGameHost` 只在 eligible 上轮询（选择时以 `UtcNow` seam **重查**——刷新死掉也不给昨天的宿主），无 eligible 时抛错并点名四种不可选因；`EligibleGameHostCount` 新增；种子默认 `Ready`/`Accepting`。
- **配对器门**：`GameHostCount==0` → `EligibleGameHostCount==0`——全舰排空/全满/全 NotReady 时配对周期直接返回，**票留在队列**等任一宿主再准入。
- **续租谓词对齐**：`RenewLiveOwnershipsAsync` 由 `lifecycle='Running'` 改为 `IN ('Running','Draining')`——排空宿主在「drain 写入 → 下次自报（≤500ms）」窗口内 lifecycle 确为 Draining，续租必须照续，否则其既有房租约流失、被夺走（违反「排空不杀旧房」）；**沉默（observed_at 过窗）才是租约流失触发器**。

**证据**（+7 fact，全部在 18935f5）：目录单元 2——NotReady/Full/Draining 四宿主 `GameHostCount=4` 而 `EligibleGameHostCount=1`、仅 game-ok 被轮询、Full→Accepting 自报回池（满宿主是暂停不是驱逐）、未知词 fail-closed 但仍可达；证据过期（`UtcNow` seam +7s > 6s 窗）选择时即失效而成员/通道不动、新自报复活。准入单元 2——`WouldRefuse` 镜像 TryReserve 两维、5 次询问不占槽、释放后转回；`AdmissionState` 随槽位 Accepting→Full（cap=1 持满）。store 2——棘轮顶住乐观自报（宿主再报 Accepting，feed 仍 Draining）且排空宿主仍列 feed；排空宿主租约照续（`RenewLiveOwnershipsAsync`=1、lease_until 推满）+ 静默（observed_at 回拨 120s）不续。宿主 1（端到端，真实 control/data/streamer/game 宿主）——`game-sched-b` 以 `CHORUS_GAME_MAX_ACTIVE_ROOMS=1` 持满自报 Full；wave1 4 mounts 两房两 owner；wave2 2 mounts 全落 `game-sched-a`；admin drain `game-sched-a` 回复 `Lifecycle=Draining`；a/b 既有房路由不动；wave3 2 mounts 票停车 6s 不 commit、房数不增。M3-7 自报词断言 `"Open"`→`"Accepting"`（遗留词入站仍容忍）。

## 持久模块恢复身份落地：房间行是身份权威 + 具名拒绝契约（FIX-MODULE-01，80aad99）

根因一句话：`game.room(module_version, config_hash, package_hash, tick_ms)` 是**只写不读**——StartRound 写进身份列后，恢复计划只从 `game.frame` 取身份，模块由「调用方 `tick_ms` + 硬编码字面量」重建（原 `RoomRuntime.RecoverUnknownRoomAsync` 顶部 `new RedesignGameModuleManifest("example-factions", "1.0.0", request.TickMs, …)`）。后果：takeover/admin 恢复传一个不同的 `tick_ms` 就**静默改掉原局的节拍**；房间持久的身份列从不参与恢复；「缺包/不兼容」没有任何错误契约——恢复只在模块读不出快照时才 park，不说「这个包我加载不了」。

- **单一身份权威**（`Chorus.Rpc.GameModuleIdentity`，新）：`Name/ModuleVersion/ConfigHash/PackageHash/RecoveryMode` 常量。协调器 `StartRound` 的三件套（原硬编码 `"1.0.0"/"cfg-1"/"pkg-1"`）改从此读；`RoomRuntime.PrepareRoomAsync` 的 manifest 也从这里取 name/version/recovery-mode（原 `"example-factions"/"1.0.0"/DeterministicReplay` 字面量）。MODULE-02 的注册表会把这里的 pin 换成真实包记录，届时恢复校验就是真正的注册表查找。

## FullCheckpoint 恢复模式落地：每帧同事务 checkpoint + 头快照直恢复不重放（FIX-MODULE-03，6209082）

根因一句话：checkpoint 节拍是一个全局字面量——`RoomActor` 固定按 manifest 的 `SnapshotEveryTicks`（100）周期性携带快照，`RecoveryMode` 只是房间行里一个被校验却不被遵守的字符串：一个声明 FullCheckpoint 的非确定性模块在旧代码下既拿不到每帧 checkpoint，恢复也只会走确定性重放——而重放一个非确定性模块按构造必然哈希链失配、只能 park，等于 FullCheckpoint 模式名存实亡。

- **第三 shipped 包 example-live**（`LiveGameModule`，`pkg-live-1`/`0.9.0`/`cfg-live-1`/FullCheckpoint）：诚实非确定性模块——每个 boost 从时钟抽 0..2 抖动（`clock` 构造注入缝：同一时钟值下 tick 可复现、跨时钟值必不同——非确定性是可脚本的证据，不是 flaky 的墙钟断言）；礼物是观众噪声。结果文档保持家族形状（ranking/winner）。
- **节拍由模式决定**（`RoomActor._checkpointEveryTicks`）：FullCheckpoint → 1，每个已提交 tick 的 `CommitFrameRequest` 携带 `SnapshotPayload/Hash/SchemaVersion` 并与帧同事务（架构 8.2：checkpoint 失败回滚整帧）；DeterministicReplay → manifest 的 `SnapshotEveryTicks`（原行为不变）。
- **prepare 持久化包的模式**：`PrepareRoundRequest.recovery_mode`（MODULE-01 迁移 0021 的列与字段）此前 game-server 一直写 data-plane 默认值——现在写**命中包记录的 RecoveryMode**，与节拍同为「prepare 时钉下的房间事实」，恢复侧的「不兼容模式」校验从此比对的是真实语义。
- **恢复分叉**：包模式 = FullCheckpoint → 取 ≤LastTick 的最新快照，要求恰在头 tick（每帧同事务 checkpoint 在构造上保证了它）；`Restore`+哈希校验通过即 `AdoptRecoveredStateAsync` 采纳（`ReplayedFrames=0`、Note「resumes without replay」——非确定性模块的重放不可能成立，恢复根本不尝试；不重 pin 头快照：头 checkpoint 已持久化，重 pin 会撞 `game.snapshot(room_id,tick_id)` 唯一约束）；快照缺失/不在头/不可读/哈希不合 → 具名拒绝 + 可见停机（`RefuseAndSuspendAsync`）——绝不回退确定性重放、绝不拿旧快照猜。确定性路径的采纳尾部与无快照尾部原样提取为 `AdoptRecoveredStateAsync`/`RefuseAndSuspendAsync` 两个私有方法（注释与 Note 字符串逐字保留，两条路径共用同一激活故事：pin（如需）→ fenced confirm → actor 起跑）。
- **proto/契约文档**：`RecoverRoomReply.replayed_frames` 注释写明模式语义（DeterministicReplay>0=自最新一致快照重放；FullCheckpoint=0=头快照直恢复）；`RedesignGameModuleManifest` 文档写明 `SnapshotEveryTicks` 只是 DeterministicReplay 模式的节拍。

**证据**（+5 fact，全在 6209082）：注册表单元 +1（`RedesignModuleCatalogUnitTests`——live 包五项事实+FullCheckpoint+shipped 清单；时钟缝非确定性证据：同钟两次运行哈希相同、异钟（jitter 1 vs 2）分数 31/32 哈希相异）；checkpoint 单元 3（`RedesignModuleCheckpointUnitTests`，新——pkg-live-1 开局后每个 commit 均带非空 SnapshotPayload/32 字节哈希 vs pkg-1 前三帧裸帧（节拍跟随包模式而非全局设置）；FC 恢复自头快照：两帧 StateHash 故意置零字节（重放语义下必驳的链）仍 Recovered=true/LastTick=2/SnapshotTick=2/ReplayedFrames=0，且恢复后 actor 自头继续提交并仍每帧带快照；FC 无头快照：只余 tick-0 快照、头在 tick-3 → Recovered=false/Suspended、Note 点名「newest checkpoint is at tick 0…cannot replay」、停机调用落入 round store（reason 带 recovery failed）、无 actor）；宿主端到端 1（`RedesignModuleCheckpointHostTests`，新，真进程拓扑+真 kill——pkg-live-1 房间推一个 boost、head≥30 且中途 frame⋈snapshot 零缺、`environment.Kill("game-a")`、等租约到期、TransferOwnership+RecoverRoom 到 game-b：Recovered=true/ReplayedFrames=0/SnapshotTick==LastTick≥30、房间在 B 自然跑完、结果红 30..32（30+一次抖动）蓝 0 红胜、终局 frame⋈snapshot 仍零缺——kill 两侧的每帧 checkpoint 都是数据面事实）。回归：M2/M3 takeover/recovery 族 34/34；M4 宿主族 10/10；模块族（catalog+load+identity+checkpoint）17/17；全量 Release 1407/1407 绿（共租负载 15.9 起且全程叠加他线峰值，6m29s；= 1402 基线 + 5）；残留 0 进程 0 库。

## 推送输入 Tick 消费落地：座位排空优先 + 帧事务原子消费（FIX-INPUT-04，363fcca）

22.9 主链路消费段闭合：INPUT-03 的收件座从「只入账」变为「本 tick 的输入来源」。机制发现是 `CommitFrameRequest.InputEventIds` 与输入来源无关——store 校验每个 ref 是该房 inbox 的 Pending delivery 并在**帧事务内**置 Consumed（FIX-FRAME-04 已交付的原子性），座位事件由耐用腿写成 Pending delivery，帧提交即消费。消费真相仍是收件箱游标（decisions §「输入事务提交后向平台确认」）：丢座/丢唤醒只损延迟，恢复路径拉取补齐。
