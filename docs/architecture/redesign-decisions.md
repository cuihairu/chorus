# 重设计关键决策

日期：2026-10-25。状态：本轮授权设计形成的方案决策，待实现验证；不冒称用户逐项审批或已完成生产验证。

## ADR-R01：身份、直播挂载、连接和对局分别建模

原因：平台启动凭证、主播长期资料、直播事件与对局结束具有不同生命周期。选择 Streamer / LiveSession / GameplayBinding / LoginSession / Room / Participation 分离模型，以数据库约束维护一直播一玩法和活跃参与唯一性。

替代方案：一个 Session 同时代表连接、主播和房间。拒绝原因：断线会错误结束游戏，换局会丢资料，多主播对战没有共同权威对象。

后果：增加显式关联与状态转换，但失败恢复可解释。覆盖 TR-domain-001～003、TR-auth-001～003。与客户端引擎无关。

## ADR-R02：七种进程角色，管理模块先不单独部署

选择 NodeAgent、ControlServer、两类 Gateway、StreamerServer、GameServer、DataServer。匹配、目录和调度是 ControlServer 的独立模块；数据投影和结算在 DataServer。

替代方案：每个 Manager 一个进程会增加启动环与事务边界；全部塞单体则不能隔离平台接入、游戏计算和数据故障。允许开发合并宿主，但必须使用同一接口、存储和所有权规则。

后果：物理扩展有清楚依据；一个 Actor 不等于一个进程。覆盖 TR-cluster-001～003、TR-runtime-001、TR-match-001。

## ADR-R03：PostgreSQL 单写主库作为首期共同事务边界

选择 ControlServer 与 DataServer 共用一个权威数据库、分 schema/权限；行锁、唯一约束与版本检查实现身份、预留、所有权和帧提交的临界事务。DataServer 提供业务读写服务，计算节点不直连写库。

替代方案：自建共识集群、Redis 锁加独立业务库、按服务分库，都会引入额外一致性协议；初期不采用。PostgreSQL 不是无容量上限，所有热写必须压测。

后果：单数据库是容量及可用性边界；首期 HA 同步复制，故障晋升先人工隔离旧主。保留旧 room-control-storage.md 中“已确认数据不丢”的意图，但替换每帧完整快照和历史磁盘估计。覆盖 TR-consistency-001～003、TR-data-001～004。

## ADR-R04：所有权 epoch 在接收端执行 fencing

选择数据库中的 OwnerInstance/Epoch/LeaseUntil，所有权变更与业务提交锁同一行；数据服务校验，不依赖心跳通知及时到达。

替代方案：只让旧实例自愿停止、只靠 Gateway 路由、只靠 NodeAgent kill，均无法抵抗网络分区。外部平台不支持 fencing 的接口单独采用 Outbox/查询/幂等/未知结果处理。

后果：数据库不可写或所有权过期时暂停权威业务。覆盖 TR-consistency-001、TR-recovery-001～003。

## ADR-R05：持久帧日志加周期快照

选择每 tick 提交有序输入、确定性信息、状态哈希和副作用记录，成功后发布；默认每 5 秒完整快照。非确定性模块必须使用每帧 FullCheckpoint。

替代方案：每帧全量 checkpoint 写放大高；纯内存 Tick 加异步日志会丢失已经发布的结果；只记录输入而不记录帧分配不能重放确定结果。

后果：模块必须提供恢复契约、跨 OS 验证，提交延迟进入 Tick 预算。覆盖 TR-runtime-001～003、TR-recovery-002、TR-data-002。

## ADR-R06：持久接收与游戏应用分开确认

选择输入事务提交后向平台确认；游戏应用由帧提交决定。通知只做唤醒，收件箱游标可恢复。应用级幂等效果不等于网络 exactly-once。

替代方案：收到回调就确认会在崩溃时丢事件；每次等待游戏执行完再回调会把慢房间放大为平台重试风暴。

后果：需要 pending/unresolved/terminal disposition 和积压运维能力。覆盖 TR-platform-001～004。

## ADR-R07：匹配采用持久预留、准备、原子提交

选择统一数据库事务提交所有参与关系与 Room Running；RPC 只进行准备和通知。取消、到期和提交使用相同锁及版本。

替代方案：两个主播分别加入再凑成对局，会产生半入场和双匹配；分布式两阶段数据库提交对首期不必要。

后果：需要回收预留、恢复协调者以及 PreparedRoom 清理。覆盖 TR-match-001～003。

## ADR-R08：跨平台 OS 的统一网络与进程执行抽象

选择 .NET 10/Kestrel、内部 gRPC/TLS、外部 WSS/HTTPS；同机也支持 loopback TCP。Linux systemd / Windows Service 只自举 NodeAgent；本地进程树控制由平台实现提供。

替代方案：首期同时维护共享内存、UDS、NamedPipe、TCP 多套协议会增加不可测组合；强制 Kubernetes 不满足独立监管要求。

后果：发布两个 RID 包，真实双 OS 验收。具体运行时支持版本以发布时官方矩阵为准。覆盖 TR-ops-001～004。

## ADR-R09：持久资产和结算由统一数据服务执行

选择幂等账本、不可变结算清单、逐笔奖励及投影 Outbox。GameServer 只产生已提交效果，不直接写资产。普通资料 dirty flush 与关键数据承诺分离。

替代方案：整个玩家 JSON 周期覆盖会覆盖并发奖励；结算回调重跑全局会重复发奖；每个游戏自写保存不满足开箱即用。

后果：提供默认 provider、迁移、账本查询、补偿和恢复工具；玩法决定奖励数值，平台支付分成仍外部负责。覆盖 TR-data-001～004。

## ADR-R10：版本钉住与自然排空优先

选择已开局固定 ModuleVersion/ConfigHash；升级默认只影响新局。原版本必须保留到相关对局恢复窗口结束。在线迁移仍使用原模块版本。

替代方案：热替换运行中的玩法程序集或数值会破坏可重放性；一键回滚数据库 schema 风险不可控。

后果：包缓存和数据库 expand/contract 迁移需要管理，回滚必须兼容已写数据。覆盖 TR-ops-002、TR-runtime-003。

## 旧决策审计与待定项

旧 decisions.md 的平台协议占位不能带入生产；旧单体拆分阶段不再约束目标拓扑；旧静态 token 只适用于测试入口。旧数据库决策是旧实现的有效历史，不在本轮修改其审批状态。

基础模块划分、协议类型、持久化、所有权、恢复、匹配、部署与升级决策已在本文件给出。没有需另开一轮设计才决定的基础 ADR。

可延后 ADR：数据库分片（单库容量门槛被证明不足时）、对象存储快照（实际尺寸超预算时）、跨地域实时部署、非受信任模块沙箱、跨平台账户合并。这些不是首期暗含承诺。
