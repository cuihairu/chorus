# 直播互动游戏重设计：领域调研与需求基线

调研日期：2026-10-25。状态：设计输入，不是最终架构或已实现能力声明。

## 用户已确定的约束

- 面向可独立部署、多节点运行的直播互动游戏服务器平台，不受现有代码兼容性约束。
- 同一直播同时只运行一种玩法。
- 持久化提供开箱即用的功能，不只提供待开发者实现的接口。
- 主播意外离线后保留一局的时间，防止中断。
- 服务器支持 Linux 和 Windows。
- Chorus 自己承担节点、进程监管和业务恢复职责。

对离线要求的设计解释：进行中的对局不因客户端断线立即销毁，保留恢复入口；建议继续运行至本局结束，不自动开启下一局。无进行中对局时的保留时长、结算后的结果保留时长作为独立配置，不能混同。此解释尚不是用户确认的完整状态机。

## 官方资料与可确认事实

这些资料公开的是接入协议和业务流程，不是抖音、快手内部服务器架构，也不是某家游戏厂商完整的分布式实现。

### 抖音

- [直播玩法接入指南](https://partner.open-douyin.com/docs/resource/zh-CN/interaction/develop/douyincloud/guide)：描述主播玩法客户端、开发者后端和平台互动数据的链路。平台示例不等于完整的权威对战后端。
- [获取直播信息](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/develop/server/live-room-scope/audience-play/get-live-info)：伴侣或云启动传入 token，由玩法服务端兑换直播间及主播身份；该页注明启动 token 有效期为 30 分钟。启动凭证和 Chorus 重连凭证应分开。
- [观众一键同玩](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/jierushuoming/advanced-interaction/audience-play)：特定能力允许连线嘉宾云启动并操作玩法；普通弹幕观众和可操作嘉宾不能混为一类。该扩展的存在不意味着所有观众都直连 Chorus。

### 快手

- [玩法技术基础能力](https://open.kuaishou.com/miniPlayDocs/technologyrelated/Affiliatedability/basicability/localdevelopment.html)：用 roomCode 建立玩法绑定；另有对局 start/stop 接口。互动回调允许乱序，礼物 uniqueNo 可用于幂等，成功回执要求 HTTP 200 与 result=1。精确重试窗口仍需核查。
- [双人连屏](https://open.kuaishou.com/miniPlayDocs/technologyrelated/Affiliatedability/basicability/Linkedscreen.html)：提供主播视频连线的生命周期接口。平台连屏和游戏内权威对战应分开管理。
- [底部栏面板](https://open.kuaishou.com/miniPlayDocs/technologyrelated/Affiliatedability/basicability/dibulan)：包含主播开启及观众加入可操作玩法的能力。作为扩展接入类型保留，不据此改变普通弹幕场景的默认模型。

## 据此推导的 Chorus 业务模型（设计建议）

1. 平台身份：至少按平台、应用、平台用户标识隔离；跨应用关联仅在有可信映射时建立。
2. 主播实体：持续业务身份与资料，不随连接或一局结束删除。
3. 直播场次：平台直播上下文，不等于主播账号或游戏对局。
4. 玩法挂载：直播场次当前运行的玩法及平台绑定状态；遵守用户的一直播一玩法约束。
5. 游戏对局：内部独立身份、参与主播、观众参与记录、权威状态及结算。
6. 观众参与：普通模式由平台事件识别，不要求每位观众建立 Chorus 登录连接；需要持久化时仍能具有玩家记录。
7. 客户端会话：主播或获授权操作参与者的连接和重连状态。
8. 平台任务：绑定、订阅、查询、停止、限流、失败重试等外部状态，不能仅用本地 socket 状态代替。

这些是逻辑对象，不能直接按对象数量划分进程。

跨主播对战应支持多个直播上下文进入同一权威对局；平台房间标识映射为内部对局与参与方，不要求平台提供 Chorus 的 MatchId 或 FactionId。

匹配切换和结算边界必须处理迟到事件：能够可靠归属旧局的事件不得静默计入新局；不能假设所有平台事件都有足够信息恢复用户操作的真实全序。完整设计进一步确定：没有可信局标识时按首次持久接收窗口归局，间歇窗口按局外规则处置；只有来源/映射冲突等无法按规则分类的输入进入待核对，避免把全部新局事件无限隔离。详见[完整设计](../architecture/architecture.md)第 6.2 节。

## 开箱即用持久化的建议交付范围

以下为根据用户要求提出的默认设计范围，不是平台要求或用户逐项确认：

- 主播及观众玩家资料、可扩展游戏数据。
- 默认数据库实现、建表迁移、配置及可运行示例。
- 自动加载、增量保存、版本冲突处理、重试与关停刷盘。
- 关键事件持久接收、去重记录与处理进度。
- 对局检查点、恢复和历史结果。
- 幂等奖励发放、资产变更流水、可重试结算。
- 常用积分、库存和排行榜能力及扩展点；具体玩法经济规则仍由游戏定义。

普通资料可周期保存，已确认的重要事件和奖励不能只依赖定时内存刷盘。平台支付分成不等于游戏内资产记账。

## 旧仓库资料中需要纠正的依据

- `docs/reference/platform-douyin.md` 的研究重点是小游戏 code2Session 等接口，不能据此判断直播小玩法的身份和互动推送能力。其直播字段与签名仍有占位契约。
- `docs/reference/platform-kuaishou.md` 引用 SaaS 加密消息协议，并明确未确认其是否适用于直播事件；不应将该协议视作已验证的直播小玩法接入协议。
- 旧映射示例要求外部事件提供 `session_id`，这不能代替内部平台绑定与路由目录。
- 本轮仅核对文档依据，没有执行代码审计或真实平台联调；不能据此声称所有现有实现均不可用，或新接入已验证通过。

## 剩余信息及获取责任

| 剩余项 | 获取方式 | 是否阻塞业务重设计 |
|---|---|---|
| 两平台各能力的权限、完整验签、批次/单事件 ID、重试窗口、失败补拉、关闭通知 | 继续核对直播玩法专属文档；公开资料不足部分用获授权测试账号联调 | 否；阻塞对应适配器生产验收 |
| 代表玩法每局时间、状态大小、每事件计算成本、恢复数据 | 用示例玩法测量；具体游戏接入时补齐恢复契约 | 否；影响容量和恢复验收 |
| 峰值主播、事件吞吐及硬件预算 | 先声明容量假设，建立基准压测，再用真实业务数据校正 | 否；不能据此提前承诺生产容量 |
| 账号跨平台关联及跨平台同局的授权条件 | 默认身份隔离、同平台匹配；后续根据官方能力及产品需要扩展 | 否；此为设计默认，不是用户确认 |
| Windows/Linux 进程监管、部署、恢复差异 | 设计自举与进程执行抽象，在两系统验收 | 否；属于实现验证责任 |

## 设计方下一步必须补齐的内容

- 启动凭证兑换、实体加载、绑定平台、登录成功、重复启动和重连的完整流程。
- 匹配预留、入场提交、取消、超时、对局结束与平台状态对账。
- 主播实体、玩法挂载、对局及平台任务各自的所有权和恢复规则。
- 网络分区时旧实例隔离、关键写入防双主、结算幂等。
- 主播断线与服务器宕机分别恢复；后者需要持久检查点和输入恢复，不能靠内存保留实现。
- 每条需求对应失败场景和验收证据，完成后才决定最终进程划分。
