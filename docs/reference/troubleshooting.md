# 故障排查

本文面向最常见的线上问题：不同步、追帧失控、慢端恢复失败、整房间一起卡。

建议结合以下文档一起使用：

- [帧同步最佳实践](../design/frame-sync-best-practices.md)
- [客户端追同步状态机](../design/client-resync-state-machine.md)
- [参数调优](./tuning.md)
- [运维与观测](./operations.md)

## 排查顺序

不要一上来就调参数，先判断问题属于哪一类：

1. 单个客户端异常，还是整房间一起异常
2. 是服务端 tick 过载，还是客户端应用/渲染过慢
3. 是轻度 lag 没收敛，还是恢复路径本身失效

如果这个分类都没做清楚，后面的处理大概率会误判。

## 现象 1：追同步时两边都追不上

典型表现：

- 一个端落后后，另一个端也开始卡
- 双方帧差没有收敛，反而一起变大
- 恢复时短时间出现大量补帧或大量消息堆积

优先检查：

1. 服务器是否还存在“等待慢端”或“暂停全局推进”的逻辑
2. 客户端是否在重度 lag 时仍试图长时间补帧
3. 是否缺少快照跳转，只能按历史帧回放恢复

最常见根因：

- 全局推进与慢端恢复耦合
- 恢复策略错误地依赖连续补帧

正确处理：

- 服务器持续推进
- 慢端超阈值后直接快照恢复
- 视觉层自己平滑，不要求逻辑层补完所有中间帧

## 现象 2：只有一个客户端经常掉队

典型表现：

- 单个客户端 `lagTicks` 持续偏高
- `resyncCount` 明显高于其他客户端
- 其他客户端基本正常

优先检查：

1. 该客户端 `lastAckAgeMs`
2. 该客户端快照应用耗时
3. 是否存在主线程卡顿、重资源加载、渲染峰值

判断方法：

- 如果只有它异常，优先看端侧性能
- 不要先怀疑服务端 tick 策略

处理建议：

- 缩减客户端快照应用成本
- 降低本地追赶预算
- 检查 ACK 是否在真正应用完成后才发送

## 现象 3：高峰期大家一起 lag

典型表现：

- 多个客户端同时 `lagTicks` 上升
- `lastTickProcessMs` 明显升高
- 高峰输入时 resync 次数一起增加

优先检查：

1. 单 tick 事件数（相邻两次 `/sessions` 的 `totalAppliedEvents` 差值）
2. `maxEventsPerTick` 是否生效
3. 事件合并/降采样是否足够
4. 快照体积是否过大

最常见根因：

- 服务端 tick 过载
- 单帧事件爆炸

处理建议：

- 先做背压，再谈追同步
- 必要时提高 `tickDurationMs`
- 高频低价值事件从权威逻辑链路剥离

## 现象 4：客户端频繁收到强制快照

典型表现：

- `forced=true, reason=\"lag\"` 的快照很频繁
- 客户端刚恢复又再次 lag

优先检查：

1. `maxLagTicks` 是否过小
2. `resyncCooldownMs` 是否过短
3. 客户端应用快照后是否真的进入 `Following`
4. ACK 语义是否正确

常见误区：

- 以为是阈值太严格

实际上很多时候是：

- 客户端恢复动作太重
- ACK 发早了
- 本地仍在做过量补帧

## 现象 5：客户端明明收到了快照，但服务器还是判定落后

优先检查：

1. ACK 是不是在“收到快照”时发送，而不是在“应用完成”时发送
2. 客户端是否把快照放入队列后就提前 ACK
3. `lastAppliedTickId` 是否真的更新到了快照对应 tick

这类问题本质上是 ACK 语义错误。

正确语义：

- `ack.lastAppliedTickId` 只表示已经完成权威状态应用

## 现象 6：轻度 lag 本来能追上，但一追就更卡

典型表现：

- 客户端一进入 `CatchingUp` 就掉帧更严重
- 追赶期间主线程负载明显升高

优先检查：

1. 每帧额外补了多少逻辑 tick
2. 追赶期间是否仍跑完整表现逻辑
3. 是否缺少每秒追赶预算上限

处理建议：

- 每渲染帧最多额外补少量 tick
- 每秒总补追数必须封顶
- 必要时在追赶期间降级部分表现层开销

## 现象 7：重连后恢复很慢

典型表现：

- 客户端重连后要等很久才能重新跟上
- 服务器持续下发很多历史数据

优先检查：

1. 是否有足够频率的周期快照
2. 是否还主要依赖历史增量回放
3. 快照体积是否过大

正确方向：

- 重连恢复应优先依赖“最新快照 + 有限增量”
- 不应依赖无限历史回放

## 快速判断矩阵

### 只有一个客户端慢

优先怀疑：

- 客户端主线程
- 快照应用性能
- 本地 ACK 逻辑

### 大家一起慢

优先怀疑：

- 服务端 tick 过载
- 单帧事件爆炸
- 快照发送/序列化成本过高

### 能收到数据但还是不同步

优先怀疑：

- ACK 语义错误
- 客户端状态机错误
- 快照应用与渲染层耦合

## 排查时必须拿到的指标

至少需要拿到：

- `tickId`（会话当前权威 tick）
- 每客户端 `lastAckTickId`
- 每客户端 `lagTicks`
- 每客户端 `lastAckAgeMs`
- `lastTickProcessMs`
- 每 tick 事件数（相邻两次 `/sessions` 的 `totalAppliedEvents` 差值）
- 丢弃/合并事件数
- 每客户端 `resyncCount`

如果没有这些指标，不建议在线上凭感觉调参数。

## 三个高频误判

### 误判 1：觉得是网络差

如果所有客户端同时 lag，更可能是服务端过载，不是网络。

### 误判 2：觉得是追帧太慢

很多时候不是追帧太慢，而是根本不该继续追帧，应该快照跳转。

### 误判 3：觉得是阈值太严格

频繁 resync 往往说明恢复动作太重或 ACK 语义有问题，不一定是 `maxLagTicks` 配小了。

## 建议的排查动作

遇到线上问题时，建议按下面顺序做：

1. 先看是否是单客户端还是全局问题
2. 再看 `lastTickProcessMs` 是否逼近 tick 周期
3. 再看客户端 `lagTicks` 和 `lastAckAgeMs`
4. 再确认是否频繁触发强制快照
5. 最后才去调 `inputDelayTicks`、`maxLagTicks`、`snapshotEveryTicks`

## 总结

故障排查最怕的是一边看现象一边乱调参数。

更可靠的方法是：

- 先区分问题类别
- 再定位是推进链路、恢复链路还是端侧性能
- 最后才做参数微调

只要你发现系统仍在依赖“长时间补帧恢复”，那就应该优先回到同步设计本身，而不是继续优化追帧细节。
