# 进程拓扑：网关拆分与房间进程（设计）

> 状态：2026-10-12 设计定稿（用户提议 + 评审对照）。属**目标形态与节奏**，实现随 todo.md 阶段推进；未达触发条件前不落地物理拆分。

## 1. 提议与结论

提议形态四类角色：

1. **平台网关**：对接抖音 / 快手等直播平台（HTTPS 回调、开放平台长连接）；
2. **主播网关**：对接主播端与直播伴侣客户端（WebSocket、ACK、重同步；英文标识 `streamer-gw`）；
3. **房间管理进程**：房间注册、分配、健康、路由表；
4. **房间进程 × N**：每个房间的权威 tick 与 GameModule。

**结论：角色划分成立，但物理进程按「角色先分、进程后拆」推进，不一次拆成四个。**

## 2. 为什么角色划分成立

- **两个故障域**：平台侧突发洪峰、验签、限流与主播侧的鉴权、ACK、重同步互不相干，分开后一边被打爆不带走另一边；限流/验证/超时各配各的（对应评审 P0-4「Ingress 默认放行」与 P1-10「客户端消息边界」）。
- **调度与执行分离**：房间注册/分配/健康/路由归 manager，权威 tick 与玩法归 worker，跨机扩展不用重构。
- **已有底座**：`Cohort.Messaging` 的 `Envelope` + UDS/NamedPipe/TCP/HTTP 就是进程间通道；现有 Gateway ↔ EngineHost 拆分模式即「主播网关 ↔ worker」的原型。

## 3. 关键事实：瓶颈是事件吞吐，不是连接数

直播互动里**观众不直连本系统**（他们连的是抖音/快手），本系统连接数只有主播端与直播伴侣，很小；真正放大的是**事件量**（弹幕洪峰）。因此：

- **不采用一房一进程**：一个房间 = 一个 `SessionActor`，单 worker 进程承载数十到上百个房间；
- **房间管理进程在单机阶段是逻辑组件**（寄宿），不是必须的物理进程；
- 扩容依据是每秒事件数与 worker CPU，不是房间数。

## 4. 阶段与触发条件

| 阶段 | 形态 | 触发条件 |
|---|---|---|
| 现在 | 单体内**代码分层**：`platform-ingress` 与 `streamer-ws` 两个 listener，两套验证/限流/超时，同进程部署（单体仍是默认部署形态） | 进行中（平台接入批次） |
| 下一步 | **四角色、三进程**：platform-gw、streamer-gw、room-worker（承载多房间）；`RoomManager` 作为逻辑组件寄宿 worker 侧，由 `MatchRegistry` 升级为房间注册 + 路由表 | todo.md 阶段一正确性五项完成 |
| 再往后 | room-worker 独立多进程/多机，room-manager 才单独成进程（房间粘性 + 快照恢复） | 单 worker 高峰 CPU > 60%，或单机房间数达数百量级 |

## 5. 拆分前必须先解决的两个前置问题

1. **房间事件的单点排序**：同一房间全部输入必须在唯一 actor 内排序（现单消费者邮箱即此职责）。拆进程靠**房间粘性**保证，不允许两处同时写同一房间。
2. **恢复路径**：房间进程重启需有权威快照可回。当前快照仅存在于内存、无持久化——先补评审阶段三的快照版本/大小上限/应用失败路径与恢复闭环，再谈跨机。

跨进程路由形态（沿用现有模式推广）：manager 维护 `房间 → worker` 映射并推送给网关；网关据此选择到 worker 的通道（或走 worker 的反向通道），主播网关与平台网关共用同一张路由表。

## 6. 明确不做

- 不上分布式 Match 集群；
- 不引入 Kafka / RabbitMQ 等外部消息平台；
- 不把平台私有适配逻辑放进核心；
- 单体保持最简单、最易调试的默认部署形态。

> 「当前最需要的是边界清楚、故障可控、结果正确，而不是更多组件。」——外部评审 §10，本设计同此口径。
