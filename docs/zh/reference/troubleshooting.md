# 故障排查

本文针对最常见的生产问题：失步、失控的帧追赶、慢客户端恢复失败、以及整个房间一起卡死。

建议与以下文档一起使用：

- [帧同步最佳实践](../design/frame-sync-best-practices.md)
- [客户端重同步状态机](../design/client-resync-state-machine.md)
- [参数调优](./tuning.md)
- [运维与可观测性](./operations.md)

## 排查顺序

不要先调参数；先判断问题属于哪一类：

1. 是单个客户端异常，还是整个房间一起异常
2. 是服务端 tick 过载，还是客户端应用/渲染过慢
3. 是轻度延迟不收敛，还是恢复路径本身坏了

若不先做这个分类，后续处理多半会误判。

## 症状 1：重同步时双方都无法赶上

典型表现：

- 一方落后后，另一方也开始卡顿
- 双方帧差不收敛，反而一起增大
- 恢复期间短暂出现大量回填帧或消息堆积

先检查：

1. 服务端是否仍有"等待慢客户端"或"暂停全局推进"逻辑
2. 客户端是否在严重落后时仍长时间回填帧
3. 是否缺少快照跳变，只剩历史帧重放用于恢复

最常见根因：

- 全局推进与慢客户端恢复耦合
- 恢复策略错误依赖持续回填

正确做法：

- 服务端持续推进
- 超过阈值的慢客户端直接按快照恢复
- 视觉层自行平滑；不要求逻辑层补齐每一个中间帧

## 症状 2：只有一个客户端频繁落后

典型表现：

- 单个客户端的 `lagTicks` 持续偏高
- `resyncCount` 明显高于其他客户端
- 其他客户端基本正常

先检查：

1. 该客户端的 `lastAckAgeMs`
2. 该客户端的快照应用时间
3. 是否有主线程卡顿、大量资源加载或渲染尖峰

如何判断：

- 仅此客户端异常时，优先看客户端侧性能
- 不要先怀疑服务端 tick 策略

处理建议：

- 降低该客户端的快照应用成本
- 调低本地追赶预算
- 检查是否在应用真正完成后才发送 ACK

## 症状 3：高峰时段所有人一起延迟

典型表现：

- 多个客户端的 `lagTicks` 同时上升
- `lastTickProcessMs` 明显上升
- 高峰输入期间重同步次数一起上升

先检查：

1. 每 tick 事件数（两次相邻 `/sessions` 调用的 `totalAppliedEvents` 之差）
2. `maxEventsPerTick` 是否生效
3. 事件合并/降采样是否足够
4. 快照大小是否过大

最常见根因：

- 服务端 tick 过载
- 单帧事件爆炸

处理建议：

- 先做背压，再谈重同步
- 必要时调大 `tickDurationMs`
- 把高频低价值事件移出权威逻辑路径

## 症状 4：客户端频繁收到强制快照

典型表现：

- `forced=true, reason=\"lag\"` 的快照非常频繁
- 客户端刚恢复又落后

先检查：

1. `maxLagTicks` 是否太小
2. `resyncCooldownMs` 是否太短
3. 客户端应用快照后是否真正进入 `Following`
4. ACK 语义是否正确

常见误解：

- 以为阈值太严格

实际上很多时候是：

- 客户端恢复动作太重
- ACK 发送太早
- 本地客户端仍在过度回填

## 症状 5：客户端明明收到快照，服务端仍判定它落后

先检查：

1. ACK 是在"收到快照"而非"应用完成"时发送吗
2. 客户端是否把快照放入队列后提前 ACK
3. `lastAppliedTickId` 是否真的更新到快照对应的 tick

这类问题本质是 ACK 语义错误。

正确语义：

- `ack.lastAppliedTickId` 仅表示权威状态应用已完成

## 症状 6：轻度延迟本可追上，但追赶反而更糟

典型表现：

- 客户端一进入 `CatchingUp` 就掉帧更严重
- 追赶期间主线程负载明显上升

先检查：

1. 每帧回填多少个额外逻辑 tick
2. 追赶期间是否仍运行完整表现层逻辑
3. 是否缺少每秒追赶预算上限

处理建议：

- 每个渲染帧最多回填少量额外 tick
- 每秒追赶总数必须封顶
- 必要时在追赶期间降级部分表现层开销

## 症状 7：重连后恢复很慢

典型表现：

- 客户端重连后很久才重新追上
- 服务端持续发送大量历史数据

先检查：

1. 是否有足够频率的周期性快照
2. 是否仍主要依赖历史增量重放
3. 快照大小是否过大

正确方向：

- 重连恢复应优先依赖"最新快照 + 有界增量"
- 不应依赖无界历史重放

## 快速判定矩阵

### 只有一个客户端慢

先怀疑：

- 该客户端的主线程
- 快照应用性能
- 本地 ACK 逻辑

### 所有人都慢

先怀疑：

- 服务端 tick 过载
- 单帧事件爆炸
- 快照发送/序列化成本过高

### 数据收到了但仍不同步

先怀疑：

- ACK 语义错误
- 客户端状态机错误
- 快照应用与渲染层耦合

## 排查时必须拿到的指标

至少需要：

- `tickId`（会话当前权威 tick）
- 每个客户端的 `lastAckTickId`
- 每个客户端的 `lagTicks`
- 每个客户端的 `lastAckAgeMs`
- `lastTickProcessMs`
- 每 tick 事件数（两次相邻 `/sessions` 调用的 `totalAppliedEvents` 之差）
- 丢弃/合并事件数
- 每个客户端的 `resyncCount`

缺少这些指标时，不建议凭感觉在线调参。

## 三个高频误判

### 误判 1：以为是网络差

如果所有客户端同时延迟，更像是服务端过载，而非网络。

### 误判 2：以为帧追赶太慢

很多时候不是追赶太慢，而是根本不该持续追赶——应该用快照跳变。

### 误判 3：以为阈值太严格

频繁重同步往往表明恢复动作太重或 ACK 语义错误，不一定是 `maxLagTicks` 设得太低。

## 推荐的排查动作

遇到生产问题时，建议按此顺序：

1. 先看是单客户端还是全局问题
2. 再看 `lastTickProcessMs` 是否逼近 tick 周期
3. 再看客户端 `lagTicks` 与 `lastAckAgeMs`
4. 再确认强制快照是否被频繁触发
5. 然后才调 `inputDelayTicks`、`maxLagTicks`、`snapshotEveryTicks`

## 总结

排查中最糟的是看着症状乱调参数。

更可靠的方法是：

- 先区分问题类别
- 再定位是推进路径、恢复路径还是客户端侧性能
- 然后才做细粒度参数调优

只要发现系统仍依赖"长时间帧回填恢复"，就应优先回到同步设计本身，而不是继续优化追赶细节。
