# 多主播帧同步、重连、离线策略与防作弊

2026-10-29 目标契约。这里的帧同步指单权威房间的逻辑帧提交及状态同步，客户端不各自决定胜负。当前实现核对见[线程模型现状](./gameserver-threading-current.md)。

## 双方同步的依据

多个主播的参与关系指向同一个 RoomId，由同一个有效 owner/epoch 的 RoomActor 处理所有参与方输入，生成唯一有序 Tick 序列。输入顺序在服务端确定并持久保存；客户端时间不能决定事件进入哪个 Tick。帧、消费记录和效果成功提交后才发布，同一版本对应同一权威状态。

每条状态包含 RoomId、Epoch、TickId、StateVersion、模块版本和配置哈希；增量额外携带 BaseVersion。客户端只对匹配房间、epoch 和基线的增量推进状态；重复/回退版本丢弃，跳号或缺基线请求完整快照。Delta 必须携带足够重建展示状态的信息；如果模块只有效果事件而没有完整增量契约，就使用快照，不能把事件清单冒充任意玩法的完整状态差分。

这保证双方对同一版本的状态收敛，不能保证不同网络下画面在同一毫秒显示相同 Tick。客户端可在受控显示缓冲中插值，预测内容必须在权威状态到达后校正，不参与奖励裁决。ACK 只报告显示/应用进度；不能让较慢主播拖住全房 Tick。记录各订阅端落后 Tick、队列丢弃、重基线次数及端到端延迟。

## 断线重连与追赶

1. 连接断开不删除参与关系，不把旧 Gateway 的迟到断开通知作用到新 ConnectionGeneration。
2. 客户端用 Chorus resume 凭据恢复，服务端轮换会话并从持久参与关系找回原局；不能信任客户端自报 RoomId，也不重新匹配。
3. 当前默认追赶方式为取得一致的已提交头部快照，原子替换客户端基线，再连续应用该头之后的增量。不是让客户端逐条补演全部离线礼物或重新发奖励。
4. 订阅建立和头部选择之间不得漏帧；服务端通过同一发布门或可续接的提交游标保证边界。客户端安装快照期间发生溢出，则重新申请更新的全量基线。
5. owner epoch 改变时中止旧流，重新解析路由，使用新 epoch 的完整快照。新局、不同 epoch 的版本不得直接相减或串成同一增量链。
6. 如果已经终局，返回冻结结果及结算状态，不重新启动战斗。如果重连尚无完整基线，操作请求按明确规则拒绝/暂缓，不接受客户端预测状态作为依据。

历史帧窗口重放可作为以后优化；当前不能假设已有“任意离线时长的增量补帧”。慢端有界队列溢出应全量追平，快端继续运行。

## 全部主播离线：玩法级策略

离线由服务端对当前有效控制会话的连接事实、心跳超时和宽限期判断；观众数为零、一个观测连接断开或旧连接通知不等于所有控制主播离线。断线、关播、主动退出、封禁、服务故障分别作为原因输入。单方离线行为由玩法的 OnHostUnavailable 决定，不能统一判负。

玩法 manifest 钉住 `AllOfflinePolicy`、`OfflineGraceDuration`、`MaxPauseDuration`、`ResumeRequiredReadyCount`、`PausedInputPolicy`。配置进入房间持久配置及 ConfigHash，运行中不得因配置更新悄悄改策略。

| 策略 | 执行语义 |
|---|---|
| ContinueToEnd | 当前基线默认：继续计算和接受符合规则的平台事件，直到终局；不替离线主播排下一局 |
| PauseAtBoundary | 全员离线超过宽限期后，在明确提交边界写入 Paused，逻辑 Tick/游戏计时冻结；持久状态可恢复，不能只停止内存计时器 |
| FinishByRule | 玩法计算中止、结束和补偿结果，经原有持久终局及平台关闭屏障，不直接删除房间 |

暂停期间礼物/点赞仍可能由平台送达。玩法必须选择有界持久暂存、局外权益/补偿处置或明确拒绝；达到上限要可观测，已接受重要事件不能丢弃。恢复时按持久接受顺序和每 Tick 预算处理，不根据新的平台到达时间重归新局。暂停导致的外部墙钟期限（租约、凭据、平台心跳）继续维护，不能跟着逻辑时间冻结。

达到配置的控制参与者人数且各自完成同一恢复基线准备后，业务服务请求房间提交 Resume 边界，再继续 Tick；未达到人数保持暂停。准备确认有期限且绑定会话/epoch，防止单端无限拖延；超时按 MaxPauseDuration 的玩法规则结束或补偿。服务崩溃后必须恢复 Paused 和剩余策略状态，不能无意启动战斗。业务暂停不等于故障 Suspended；epoch bump 测试也不能冒充全员离线。

## 防作弊与可信边界

| 风险 | 服务端措施 |
|---|---|
| 自报胜负、积分、资产 | 只接受操作意图，合法行为和奖励由权威玩法/已提交效果决定 |
| 冒充主播、跨房操作 | 验证有效会话、租户/游戏、参与关系、连接代；不信任客户端身份字段 |
| 伪造礼物和点赞 | PlatformGateway 验证官方来源；客户端命令不进入平台礼物事实通道 |
| 重放命令、修改 payload | CommandId/EventId 去重和请求指纹；同 ID 不同内容拒绝；客户端序号与频率限制 |
| 超频、非法动作或时间作弊 | 服务端按 Tick 校验冷却、资源、状态条件、动作大小；客户端时钟不参与裁决 |
| 旧 owner 或旧路由仍写 | 接收和存储边界校验 epoch、owner、状态及租约；GM bump 后同样生效 |
| 伪造 ACK 或客户端哈希 | ACK/哈希只用于同步诊断，不作为发奖或诚实证明；可见状态按权限裁剪 |
| 断线逃避不利结果 | 离线规则、暂停次数/期限由玩法明示并持久执行，客户端不能任意暂停全房 |

TLS 和校验不能消除所有外挂；自动操作、合谋和获授权客户端窃取可见信息仍需玩法限制与行为分析。服务端权威首先保证客户端不能直接改最终状态。

## 实现边界

现有：RoomActor 串行 Tick、提交后发布、RoomSubscriber 有界队列、快照基线、epoch 失配重订阅及 WSS 重连接线。待实现/验证：直接推送迁移、通用客户端增量应用契约、暂停/恢复的持久状态及计时器、全员离线策略、完整业务命令防作弊规则与端到端证据。不得用单元测试总数宣称这些场景全部通过。
