# 帧同步最佳实践

本文聚焦两个目标：

- 给出一套适合直播互动/轻对战场景的可落地帧同步方案
- 解释为什么旧式“追帧/暂停”方案容易出现“两边都追不上”

相关背景可结合阅读：

- [帧同步设计](./frame-sync.md)
- [整体架构](./architecture.md)
- [旧服问题分析](./legacy-real-server-analysis.md)

## 先给结论

如果项目已经出现“追同步时两边都追不上”，通常不是追帧算法不够激进，而是同步架构本身选错了。

更稳的做法不是：

- 服务器等待最慢端
- 客户端长期依赖补帧回放追赶

而是：

- 服务器持续推进权威 tick
- 输入按统一 tick 结算
- 慢端超过阈值后直接吃快照对齐
- 表现层用插值/过渡掩盖跳变

一句话概括：

> 不要让全局逻辑等慢端；让慢端单独重同步。

## 为什么会出现“两边都追不上”

这是旧式事件锁步/输入帧广播实现里最常见的失控路径：

1. 服务器按时间尽力发帧，而不是严格固定 tick。
2. 某个客户端因为卡顿、GC、渲染阻塞或网络抖动开始落后。
3. 服务器为了“等它”，暂停或减慢新帧推进。
4. 快端也被迫停住，双方体验一起变差。
5. 一旦恢复，服务器和客户端又尝试连续补很多帧。
6. 连续补帧导致网络包变大、单帧事件堆积、客户端主线程更卡。
7. 系统进入“越追越落后”的正反馈。

这类问题不是局部 bug，而是策略错误：把“全局推进”与“慢端恢复”耦合在了一起。

## 推荐架构

推荐采用“服务器权威 Tick + 状态快照”的模式：

- 服务器维护唯一权威 `tickId`
- 服务器按固定 `tickDurationMs` 推进逻辑
- 输入先进入缓冲，再调度到 `tick + inputDelayTicks` 统一结算
- 客户端通过 `ack.lastAppliedTickId` 上报自己已应用到的进度
- 服务器发现客户端落后过多时，只对该客户端下发强制快照

这也是本项目当前文档和引擎实现所采用的方向。

## 最重要的原则

### 1. 服务器绝不能因为慢端而暂停全局逻辑

服务器必须持续推进权威 tick。

原因很简单：

- 慢端问题通常是局部问题，不应拖死全局
- 直播互动场景更强调“整体流畅”和“房间持续运转”
- 一旦全局暂停，快端也会被拖入追帧和爆帧

正确做法是：

- 慢端轻度落后时，允许它本地温和追赶
- 慢端重度落后时，直接发快照让它跳到最新权威状态

### 2. 输入和状态不要混为一谈

输入同步只负责“事件在什么 tick 生效”，状态同步负责“客户端如何恢复到权威状态”。

不要试图只靠补输入帧解决所有问题。因为：

- 输入回放链路长，恢复慢
- 回放期间客户端仍然要承担逻辑计算和渲染压力
- 一旦缺帧跨度大，恢复成本会指数变坏

推荐组合是：

- 日常：输入按 tick 结算
- 恢复：快照为主，必要时只回放少量增量

### 3. 逻辑层和表现层必须拆开

逻辑层只认权威 tick，不做花哨补偿。

表现层负责：

- 插值
- 过渡动画
- 镜头与 UI 平滑

如果把逻辑追帧和视觉补偿混在一起，最终会同时损害公平性和稳定性。

### 4. 每 tick 必须有背压

每个 tick 处理的事件数必须有硬上限，例如 `maxEventsPerTick`。

超过上限时，必须执行以下一种或多种策略：

- 合并同类事件
- 对高频低价值事件降采样
- 丢弃过时事件
- 将非关键表现型事件异步化，不进入权威逻辑

否则高峰期很容易出现“单帧爆炸”：

- 单帧包体过大
- 序列化/反序列化时间过长
- 客户端一帧处理过多事件
- 结果是更严重的 lag

## 推荐的追同步策略

追同步不要只靠一种手段，应该分档处理。

### 轻度落后

条件示例：

- `lagTicks <= 3~5`

策略：

- 客户端允许短时间内略高于正常速度推进
- 每个渲染帧最多额外执行少量逻辑 tick
- 必须设置追赶上限，避免把主线程打爆

适用场景：

- 短暂网络抖动
- 一次性渲染卡顿
- 轻微的时钟漂移

### 中度落后

条件示例：

- `lagTicks > 5~10`

策略：

- 服务器向该客户端单独发送 `forced snapshot`
- 客户端直接切换到 `snapshot.tickId`
- 视觉层自己做平滑收敛，不要求逻辑层补完所有中间帧

适用场景：

- 客户端几百毫秒以上的停顿
- 网络波动导致 ack 明显滞后
- 本地补追已经无法在短时间内收敛

### 重度落后或长时间无 ACK

条件示例：

- `lastAckAgeMs` 持续过大
- `lagTicks` 长时间超过阈值
- 同一客户端频繁 resync 仍无法稳定

策略：

- 丢弃过旧增量
- 保留最新快照和有限窗口内的少量增量
- 必要时重建本地状态

这时不要执着于“从历史帧一帧不差地补回来”，那通常只会继续恶化。

## 推荐参数区间

以下建议更适合直播互动、礼物/弹幕驱动玩法，作为初始参数比盲调更稳：

- `tickDurationMs`: `50` 或 `66`
- `inputDelayTicks`: `2~4`
- `snapshotEveryTicks`: `2~5`（注：本仓代码默认 `1`，即每 tick 都发——`src/Chorus.Engine/Session/SessionConfig.cs:6`）
- `maxLagTicks`: `6~10`（注：本仓代码默认 `50`——`src/Chorus.Engine/Session/SessionConfig.cs:8`，远高于本推荐区间；调优时以观测为准）
- `resyncCooldownMs`: `1000~3000`
- `maxEventsPerTick`: 必须按压测结果配置

调参时的基本原则：

- 如果网络抖动明显，优先适度增大 `inputDelayTicks`
- 如果恢复太慢，优先提升快照频率，而不是提高追帧强度
- 如果服务端 tick 耗时逼近 tick 周期，先削峰和背压，不要继续提频

## 什么时候该用纯锁步

纯输入锁步或 rollback 并不是不能用，但前提比直播互动场景苛刻得多。

更适合纯锁步/rollback 的条件：

- 玩家数量少
- 输入频率高且公平性要求极强
- 逻辑可严格确定性复现
- 客户端性能与平台差异可控

如果你的场景是：

- 观众弹幕/礼物驱动
- 事件量波动大
- 客户端设备差异大
- 更看重整体稳定性和观感

那么“服务器权威状态同步”通常比“纯输入锁步”更合适。

## 最容易犯的错误

以下做法最容易把系统带进失控状态：

- 用暂停服务器的方式等待慢端
- 用长时间连续补帧的方式处理大跨度落后
- 客户端主要按本地时钟跑，服务器只做外环纠偏
- 单帧事件数量没有上限
- 只保存历史帧，不保存快照
- 没有按客户端维度做 ack、lag、resync 观测

## 必须具备的可观测性

没有指标，排查“不同步”基本靠猜。

建议至少记录以下指标：

- `serverTick`
- `clientLastAckTick`
- `lagTicks`
- `lastAckAgeMs`
- `lastTickProcessMs`
- 每 tick 事件数
- 每 tick 丢弃/合并事件数
- 强制快照次数
- 单客户端出站队列积压：`OutboundClientQueue.Dropped`（每客户端 latest-wins 槽被替换掉的快照数）已导出到 `/sessions` 的每客户端 `clientQueueDropped` 与 session 汇总 `totalClientQueueDropped`，指标 `chorus_client_queue_dropped_total`（`6d738b7`）。容量为 1 的槽只有「丢弃」这一种积压信号，槽深度无意义

重点看三个危险信号：

- `lagTicks` 持续增长
- `lastTickProcessMs` 接近或超过 `tickDurationMs`
- 单 tick 事件数在高峰期暴涨

如果这三个信号同时出现，通常说明问题根源不是“追帧逻辑不够聪明”，而是系统已经过载，必须先处理背压和恢复策略。

## 一套落地判断标准

如果要快速判断当前方案是不是健康，可以用下面这几个标准：

- 单个客户端掉线或卡顿时，其他客户端是否还能继续正常看到房间推进
- 某客户端落后后，是否能在有限时间内通过快照恢复，而不是无限补帧
- 高峰输入时，系统是否会主动合并/丢弃低价值事件，而不是让单帧无限膨胀
- 是否能通过指标直接看出 lag 来源：网络、客户端主线程、还是服务端 tick 过载

只要其中两三项做不到，就不要继续微调追帧参数，应先回到同步架构本身重构。

## 建议的实现顺序

如果项目正从旧式追帧逻辑迁移，建议按这个顺序推进：

1. 先建立服务器权威固定 tick。
2. 增加 `inputDelayTicks`，让输入统一按 tick 结算。
3. 为客户端建立 `ack.lastAppliedTickId` 机制。
4. 引入周期快照与强制快照。
5. 去掉“服务器等待慢端”的逻辑。
6. 最后再细调客户端本地轻度追赶策略和表现层平滑。

这个顺序的关键点是：先把恢复闭环建出来，再优化追赶体验。

## 总结

帧同步要稳定，不靠“更凶猛地追帧”，而靠正确的职责分层：

- 服务器负责权威推进
- 同步层负责缓冲、ACK、快照和恢复
- 客户端表现层负责平滑

当系统已经出现“两边都追不上”时，优先检查的不是追帧速度，而是这三个问题：

- 服务器是否还在等慢端
- 恢复是否还主要依赖长链路补帧
- 单 tick 是否已经失去背压

只要这三点改对，追同步问题一般会从“经常失控”变成“可观测、可恢复、可调优”。
